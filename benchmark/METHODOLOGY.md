# Methodology (pre-registered)

This file describes the experiment as designed **before** the main benchmark ran. It is frozen by
`FREEZE.json` (SHA-256 of every design file, written by `scripts/freeze.py` before the main run). Changes made after
the freeze are listed in §10 with the reason; none were made after seeing main results.

## 1. Question and hypotheses

Can a structured, domain-specific workflow (the Hire Your McK skill) improve the quality of strategic reasoning
beyond what the same frontier model achieves with ordinary prompting?

- **H1 · Storyline coherence:** governing thought, executive summary, titles and evidence form a more consistent hierarchy.
- **H2 · Strategic judgment:** recommendations are more defensible; alternatives, trade-offs and decision-relevant evidence are weighed better.
- **H3 · Evidence discipline:** fewer unsupported claims, invalid inferences and numerical errors.
- **H4 · Hypothesis revision:** when evidence contradicts an initially plausible hypothesis, it is revised or rejected rather than rationalised (and kept when the evidence supports it).

Co-primary outcomes (set after the pilots, before the freeze; see §10):
1. **Pairwise preference** from the pairwise judge: order-balanced win rate of C vs A and C vs B on "overall", and
   per hypothesis on "coherence" (H1), "judgment" (H2), "evidence" (H3) and "revision" (H4).
2. **Weighted rubric score** (§6) from the primary automated judge.

Secondary outcomes: dimension scores, error counts, coverage of answer-key items, defensibility, hypothesis
handling, the secondary judge, and human reviewers (when collected).

Mapping: H1 → storyline coherence score, pairwise "coherence"; H2 → strategic judgment score, defensibility,
trade-offs, pairwise "judgment"; H3 → evidence & reasoning score, unsupported claims per 1,000 words, numerical
errors, contradictions, missed critical evidence, pairwise "evidence"; H4 → hypothesis handling appropriate,
noticed contradictions, pairwise "revision".

## 2. Conditions

| | Prompt | Skill | Everything else |
|---|---|---|---|
| **A · Vanilla** | the common task (`prompts/conditions/task.md`) | none | identical |
| **B · Strong baseline** | the common task + six generic method bullets (hypothesis-driven, pyramid, MECE, exec summary first, action titles, evidence-based recommendation) written for this study, not copied from the skill | none | identical |
| **C · Hire Your McK** | `/hire-your-mck` + the common task | plugin 1.2.0 from a frozen snapshot of `plugin/` (tree SHA-256 in each run's `meta.json`) | identical |

Identical for all: model `claude-opus-5-5`, effort `high`, subagent model `claude-opus-5-5`, Claude Code version
(recorded), tools Bash · Read · Write · Edit · Skill · Agent, the same Python environment (the skill's declared
requirements, `env/requirements-gen.txt`), and a sandbox with **no network** and no read access to this repository,
`~/.claude` (except shell snapshots) or other runs. Web tools are denied. No user CLAUDE.md, memory, settings,
MCP servers or other plugins are loaded (`--setting-sources ""`, auto-memory off). Sampling parameters cannot be
set in Claude Code (and Opus 5.5 rejects them); effort is fixed instead.

**The checkpoints.** The skill is designed to stop for a human 3–4 times. The common task says the user is not
available and asks the model to choose its recommended option and carry on. If a session still ends without a
deliverable, a fixed reply (`prompts/conditions/autoreply.md`) is sent, up to 4 times, identically for every
condition. This replaces the human partner the skill expects; the benchmark therefore measures the unattended
skill, not the skill with a human in the loop.

**Mode.** The skill picks its own mode. The common task does not ask for a length or mode.

## 3. Cases

Five fictional companies, synthetic but internally consistent data generated by `cases/models.py` and written by
`cases/build_cases.py`. Every packet carries a synthetic-data banner. None reuses an existing repository example.

| Case | Decision | Initial hypothesis in the pack | Expected handling |
|---|---|---|---|
| c1 · Onsoo Botanicals | Enter the US, and by which route | CEO: Amazon-led launch | keep, with conditions (control case: the evidence supports it) |
| c2 · Harlow Fresh Markets | Reverse margin decline | CFO/COO: wage inflation is the cause; cut labor 8% | revise |
| c3 · Brightwork | Launch an AI assistant, and how to package it | CPO: $149 add-on, $8M from a survey | revise (launch yes, sizing/packaging no) |
| c4 · Palisade Docs | Raise prices while churn rises | CFO: +12% everywhere vs CEO: no increase (two competing readings) | revise (segment) |
| c5 · Parcelbird | Enter a fast-growing, structurally unprofitable market | Founders: enter now; density will fix it | reject |

c4 and c5 are the adversarial revision tests; c1 guards against rewarding contrarianism. Packets present
management's views as context only; no prompt asks the model to evaluate or change them.

Each case has a hidden answer key (`answer_keys/`): insights, required calculations with expected values, critical
evidence, traps, trade-offs, plausible recommendations marked defensible / conditional / not, and criteria for a
defensible conclusion. Generation sessions cannot read the keys (sandbox + permission deny), and transcripts are
audited for any access (`scripts/audit_runs.py`).

## 4. Runs

- **Pilot:** c2 and c5 × 3 conditions × 1 generation. Used only to validate the pipeline; excluded from results.
- **Pilot 2:** c1 and c4 × 3 conditions × 1 generation, after the changes in §10, to validate the revised packets,
  the calibrated rubric and the full evaluation pipeline (both judges, pairwise, analysis). Also excluded.
- **Main:** 5 cases × 3 conditions × 3 generations = 45 runs, in a seeded random order (`runs/main/schedule.json`,
  seed 2027), up to 3 in parallel.
- **No selection.** Every main run is evaluated. A run is restarted from scratch only when the session itself fails
  for an infrastructure reason (API error status, usage limit, machine sleep, no result event), never because of
  what the model produced; every attempt is kept (`attempts` in `meta.json`, transcripts and raw workspaces). The
  machine is kept awake with `caffeinate` during runs. A run that ends without a usable deck is
  evaluated as what it is: the judges see whatever text exists, or a note that nothing was delivered.

## 5. From deck to blind document

1. `extract_deck.py` dumps the delivered `.pptx` deterministically (text in reading order, tables, native chart
   data, notes, a marker per picture); if no deck exists, the largest Markdown/text deliverable is used.
2. `evaluate.py normalize`: an isolated Opus 5.5 session (no tools except Read for pictures, no settings) maps the
   dump to a common schema (governing thought, executive summary, slides with claims and evidence, recommendation,
   alternatives, assumptions, next steps) **verbatim, without adding or improving anything**. A deterministic
   fidelity check (word-trigram overlap with the dump) is stored per run.
3. `evaluate.py blind`: each run gets a random id (seed 4242). The judge document is the normalised storyline
   followed by the full slide text. Product-specific markers are scrubbed (the skill's name, the
   "ILLUSTRATIVE — DATA NEEDED" sticker, issue-tree code prefixes such as "2a:", "BACKUP:", source-workbook file
   names, page numbers). Structure that is part of the reasoning (an issue tree, a "what we did not pursue" page)
   is not removed, so blinding is imperfect; the judges' guess of the source is recorded as a blinding check.

## 6. Evaluation

**Rubric** (`prompts/eval/rubric.md`, anchors for 1, 3, 5): problem framing 15%, storyline coherence 25%,
evidence & reasoning 25%, strategic judgment 25%, clarity & concision 10%. The rubric explicitly tells judges not
to reward length, formatting, vocabulary or template compliance. Hire Your McK's own `check.py` is **not** used to
score reasoning; its result is reported only among the end-to-end metrics.

**Automated judges** (isolated, tool-less, settings-free sessions that see only the blind id, the pack, the key
and the document):
- primary: `claude-fable-5-2`, effort high — a different and stronger model than the generator;
- secondary: `claude-sonnet-5-5`, effort high — for judge-to-judge agreement;
- pairwise: `claude-fable-5-2`; for each case and replicate, A–C, B–C and A–B, each shown in **both orders**; a win
  counts only when both orders agree.

All judges are Claude models: self-preference toward Claude-written text is shared by all conditions, but a
preference for one condition's style cannot be ruled out. Automated grades are reported as automated, never as
human expert evaluation.

**Counted measures:** unsupported claims (and per 1,000 words of deck text), numerical errors, material logical
contradictions, missed critical evidence, insights reached, calculations correct, trade-offs identified, traps
fallen into, recommendation defensible, hypothesis handling appropriate, contradictions noticed, assumptions
challenged, uncertainty acknowledged, unsupported causal claims.

**Human review:** `scripts/make_human_eval.py` builds a self-contained HTML app and CSV forms with a different
random order per reviewer (3 by default). Reviewers see the same blind documents, pack, key and rubric.
Agreement: Krippendorff's alpha (interval) per dimension; human–judge Spearman correlation.

## 7. Analysis plan

- Unit of replication: the **case** (n = 5). Replicates estimate within-case variability.
- Per condition: mean weighted and dimension scores with 95% hierarchical bootstrap intervals (resample cases, then
  replicates; 10,000 draws).
- Paired comparisons C–A, C–B, B–A: per-case mean difference; bootstrap CI; exact sign-flip test across cases
  (smallest attainable two-sided p with 5 cases is 0.0625, so **no case-level test can reach p < 0.05**); a
  run-level permutation test within case is shown as a secondary, optimistic test.
- Win rates: rep-matched absolute-score comparisons and order-balanced pairwise judgments.
- Errors, hypothesis-revision success (overall and by expected handling), cost, time and tokens, within-case SD.
- Robustness: secondary judge; length–score correlation within condition; blinding check.
- Language: we report "consistent with", "no detectable difference", or "uncertain" and do not claim
  significance unless the interval excludes zero **and** both judges agree in direction; even then, with 5 cases,
  the result is described as preliminary.

## 8. End-to-end product evaluation (separate)

`e2e_metrics.py`: deck delivered and readable, slides, native charts vs pictures, tables, source workbook present,
share of deck numbers found verbatim in the pack, share of content slides citing a source, and (C only) the
product's own `check.py` result. Visual quality is left to human review of the decks themselves.

## 9. Threats to validity

Small n (5 cases); synthetic cases written by the same team that runs the study; one generator model; Claude
judges; imperfect blinding (deck structure is recognisable); length differences between conditions; the unattended
setting removes the skill's human checkpoints; no web research, so the skill's web-verification layer is idle;
the evidence packets are short compared with real engagements; answer keys reflect the authors' view of a
defensible answer.

## 10. Changes after the pilot (all made before the freeze and before any main run)

Pilot 1 findings and the changes they caused. None of the changes is specific to a condition.

1. **Harness: shell snapshots.** The first pilot attempt denied the sandbox all of `~/.claude`, which includes the
   shell snapshots the Bash tool sources; every condition lost its PATH (`ls`, `python3` missing). Aborted after
   ~5 minutes, kept in `runs/_aborted/`; the deny list now spares `~/.claude/shell-snapshots` only.
2. **Harness: machine sleep.** One pilot run failed when the Mac slept ("computer went to sleep mid-response").
   Runs now hold `caffeinate`; the retry rule in §4 covers this case explicitly.
3. **Harness: structured output.** `--json-schema` rejects the `$schema` key; it is stripped. Failed model calls now
   write `*.error.json` instead of an empty result, so they are retried rather than silently skipped.
4. **Blinding.** Navigation leftovers that identify the skill's layout (section-tracker lines, "p. 5–8" page
   references, lone node-code badges) are now scrubbed, like the other markers in §5.
5. **Ceiling effect → more realistic packets.** The four pilot outputs judged under the first rubric all scored
   4.40–4.75 (weighted), so the absolute scores could barely separate conditions. Each packet gained a short
   "Other material" section of the kind real board packs contain: a definitional inconsistency (c1 trade-press
   market size; c4 undefined dashboard churn), a stakeholder claim that reads correlation as causation or asserts
   without evidence (c1 retail-halo correlation; c2 "promotions work"; c3 "Copilot would win back a third of lost
   deals"; c4 "onboarding will halve churn"), a flawed internal metric (c2 e-commerce "6.1% margin" that omits
   delivery), a survey response-rate note (c3), and, in c5, evidence that partly **supports** the founders (a
   competitor turned contribution-positive in its densest city after adding a fee), so that a one-sided "no" is
   not automatically rewarded. Answer keys gained the matching items (insights, traps, evidence).
6. **Rubric calibration.** Judges used only 4 and 5. A "use the whole scale" paragraph now defines 5 as "nothing
   material to fix on this dimension" and lists flaws that cap a dimension at 4. The weights, dimensions and
   anchors are unchanged.
7. **Cost accounting.** `meta.json` now also records the cost of all attempts, including infrastructure failures.

Pilot 2 (revised packets, calibrated rubric): the first two outputs judged still scored 4.65 and reached every
answer-key insight. We did not make the cases harder again: piling on traps until the conditions separate would
tune the benchmark to its result. The ceiling is reported as a finding; the pairwise judge and the error counts are
the more sensitive measures.

Primary outcome. In pilot 2 the primary judge gave all five outputs a weighted 4.65 (a ceiling), while the
pairwise judge separated them and agreed with itself in both presentation orders in 4 of 4 pairs. The pairwise
preference was therefore made a co-primary outcome (§1). This was decided on pilot data only and favours no condition.

Environment observation: Claude Code's built-in skills (e.g. `dataviz`) are available to every condition, and the
baselines used `dataviz` for chart guidance. "Vanilla" therefore means default Claude Code, built-in skills included.

Pilot observation kept as a finding, not changed: in every pilot case the skill chose its 30–60-slide deep-deck
mode on its own (42 and 50 slides), against 14–22 slides for the baselines.

## 11. Deviations after the freeze (before any main-benchmark scoring)

1. **PDF decks.** One main run (main-c5-B-r1, strong baseline) did not find python-pptx and delivered its deck as a
   PDF drawn with its own script. §5 only foresaw a `.pptx` or a Markdown/text fallback, which would have scored the
   run's README instead of its deck. `extract_deck.py` now extracts PDF decks page by page (text in reading order;
   no chart data) and prefers a PDF over Markdown. Made before any main run was blinded or judged; it affects only
   that run. `FREEZE.json --verify` therefore lists `scripts/extract_deck.py` and `env/requirements-analysis.txt`
   as changed; the audit and evaluation scripts also received parsing fixes (a transcript event whose `message`
   is a string; `../` path normalisation) that do not change any score.
2. **Extraction bug found after the first scoring pass (v1), fixed, and the whole evaluation re-run (v2).**
   Reading the judges' rationales showed that 8/15 (Fable 5.2) and 12/15 (Sonnet 5.5) Hire Your McK documents were
   criticised for "section dividers that all carry the first section's title". The decks did not have that flaw:
   `extract_deck.py` titled each navigation slide (agenda tracker, appendix divider) with its biggest list item
   instead of its "Contents"/"Appendix" heading. This was a measurement error that disadvantaged one condition.
   The title rule now uses a navigation heading when it is the slide's largest text, and PDF pages skip running
   headers. The fix changed the text of 15/15 C decks, 1 A deck and 1 B deck (the PDF run). Every document of
   every condition was then re-normalised and re-judged (absolute: both judges; pairwise: all 90), with the same
   blinding ids, rubric, prompts and models. **v2 is the reported result**; v1 is archived unchanged in
   `eval/_v1-extraction-bug/` and summarised in the report for transparency.
3. **Analysis additions after scoring, all labelled in the outputs.** `analyze.py` gained an *exploratory* weighted
   score without the clarity & concision dimension (to check whether differences are only a length penalty), a
   pairwise figure and cost totals; `examples.py` (new) picks representative comparisons by fixed rules;
   `slim_transcripts.py` (new) writes committed transcript copies with base64 slide previews replaced by their
   hashes. None of these changes alters a pre-registered measure.

## 12. Exploratory arm C2: the skill in its full-deck mode (added after the main results)

**Why.** In every main run the skill chose its 30–60-slide `deck_deep` mode on its own, because its mode rule
recommends that mode for a CEO or board decision. The main result therefore compares the deep-deck mode with
ordinary prompting, not the skill as a whole. C2 tests the skill's default full-deck mode (`deck_detailed`).

**Status.** Added on 2026-11-16, *after* the main v2 results were known. It is exploratory, reported separately,
and does not replace or re-weight any pre-registered main result. This section was written, and
`FREEZE-explore-c2.json` recorded, before the first C2 run started.

**Design.** Identical to condition C (same frozen skill snapshot `132dffb7…`, model, effort, tools, sandbox,
packets, auto-reply, limits, Claude Code version) except that the request names the mode:
`/hire-your-mck Mode: full deck with data (`deck_detailed`).` followed by the common task. The skill's own rule
is to skip the mode question when the request names one; no skill file changes. Phase `explore-c2`: 5 cases × 3
replicates = 15 runs, order seeded (2028), parallel 3.

**Evaluation.** The same pipeline and prompts: audit, extraction (v2), normalisation, scrubbing, both absolute
judges, and pairwise judging (Fable 5.2, both presentation orders). C2 documents get fresh blind ids drawn so they
cannot collide with main ids. The main A, B and C documents and their v2 absolute judgments are reused unchanged.
New pairwise comparisons, replicate-matched as in the main benchmark: C2 vs A, C2 vs B, and C2 vs C.

**Outcomes, fixed now.**
- Pairwise preference (order-balanced score, consistent wins) for C2 vs A, C2 vs B, C2 vs C (primary judge).
- Paired case-level weighted-score difference C2 − A, C2 − B, C2 − C, primary and secondary judge, with the
  hierarchical bootstrap and sign-flip test of §7; per-dimension means; the exploratory no-clarity score.
- Mode check: share of C2 runs whose transcript shows `deck_detailed` (a run that switched to `deck_deep` stays
  in the analysis as a C2 run and is flagged).
- End-to-end: slides, words, cost, time, source workbook, native charts, `check.py` result.

**Caveats fixed now.** The C2 absolute judgments are made on a later date than the main ones, by the same model
ids and prompts; a small drift cannot be ruled out, which is why the pairwise comparison (judged fresh, both
documents in one call) is listed first.

**Changes after `FREEZE-explore-c2.json` (made while C2 generation was running, before any C2 document was
normalised or scored).** `audit_runs.py` and `e2e_metrics.py` now take "is this a skill condition" from the
config's `plugin` flag instead of the letter C (main outputs re-checked: identical). `analyze.py`'s pairwise
summary takes the comparisons as a parameter (default unchanged). `scripts/explore_c2.py` (new) blinds, judges,
pairs and analyses the C2 arm. Mode check rule: a run counts as `deck_deep` if it read the skill's
`references/deep-deck.md`; this rule classifies all 15 main C runs as `deck_deep`.

## 13. Development arm E1: the skill with a decision audit (added after the main, C2 and slide-review results)

**Why.** In the main and C2 results, and in the author's slide review (`eval/human-slides/results.md`), the skill
reached the same answers as the baselines but lost on decision completeness: known costs left out of headline
numbers, an obvious smaller alternative never tested, no threshold at which the recommendation fails. The strong
baseline's six lines ask for alternatives, assumptions and risks; the skill's main workflow had no such step.
E1 adds one change to the skill, a decision audit (SKILL.md Step 2b), and nothing else.

**Status.** Development, not a confirmatory test. The five cases are the same as in the main benchmark, their
results were known while the change was designed, and the change was written after reading B, C and C2 decks for
c2 and c5. Any claim of improvement must come from new held-out cases, designed and frozen before they are run.
This section and `FREEZE-dev-e1.json` were written before the first `dev-e1` run; one smoke run (`dev-e1-smoke`,
c2 replicate 1) checked the harness and is excluded from every result.

**Leakage check.** The skill text names no case-specific item (no wage rise, no store pilot, no growth threshold
from the cases); its examples use the skill's own fictional Cobalt Ledger. The audit's generic prompts ("a
smaller, staged or pilot version of what you reject") are standard practice but were chosen with c5 in view.

**Design.** Identical to C2 (request names `deck_detailed`; same model, effort, tools, sandbox, packets, auto-reply,
limits) except the skill snapshot, which adds the decision audit (commit `f5b01a4`). Claude Code is 2.1.326
(C2: 2.1.325). Phase `dev-e1`: 5 cases × 2 replicates = 10 runs, order seeded (2029), parallel 3.

**Evaluation.**
- Same pipeline: audit, extraction, normalisation, scrubbing, both absolute judges; fresh blind ids.
- Pairwise (Fable 5.2, both orders), replicate-matched on replicates 1–2: **E1 vs C2** (the audit's effect, same
  mode) and **E1 vs B** (the remaining gap). B and C2 documents and judgments are reused.
- Decision completeness (secondary measure). Per case, Fable 5.2 wrote a checklist of binding constraints,
  alternatives to test and key sensitivities from the pack and answer key alone, before any E1 document was
  scored (`eval/dev-e1/decision_reference/`, frozen with this section). Sonnet 5.5 then applies it to every E1,
  B and C2 document of replicates 1–2: share of constraints reflected, alternatives tested, sensitivities
  quantified; overclaim; omissions; unsupported assumptions.

**Reading rules, fixed now.**
- The audit "worked" on the development cases only if E1 beats C2 pairwise (overall preference > 0.5, E1 ahead
  in at least 4 of 5 cases) **and** decision completeness improves. If completeness improves but pairwise does
  not, or the reverse, no improvement is claimed.
- E1 vs B is reported as the remaining gap. The held-out target, to be frozen with the held-out cases, is
  non-inferiority to B (overall preference ≥ 0.45), not superiority.
- If E1 is not better than C2 here, the held-out test is not run for E1, and the published write-up reports the
  development result as a failed fix.

**Smoke run (excluded).** `dev-e1-smoke-c2-E1-r1`: complete, `check.py` 0 fail, a full `decision_audit`, 23
slides, $9.10 and 56 minutes (C2 averaged about $5 and 18 minutes): the audit roughly doubles the cost of a run.

## 14. Development arm E2: the audit turned into a plan (added after the E1 results)

**Why.** E1 beat C2 9–0 and raised decision completeness, meeting both §13 rules, but lost to B 0–10. In 18 of
20 verdicts the judge called E1 the leaner document; it preferred B for decision gates and triggers (17 of 20)
and stress or downside cases (13 of 20), and in 9 of 20 it noted that E1 was candid about a shortfall but did not
close it. E2 keeps the E1 audit and adds three steps (SKILL.md Step 2b, items 5–7; commit `acde5ce`): size the
options that close a missed target, show the headline in a base and a stress case, and turn the failure
threshold and key risks into 2–5 decision gates on main-deck slides. `check.py` DA-05..07 enforce them.

**Status and design.** Development, same caveats as §13; the change was written after reading the E1-vs-B
verdicts, so it is tuned to this judge's stated reasons, and only held-out cases can show whether it generalises.
Identical to E1 except the skill snapshot. Phase `dev-e2`: 5 cases × 1 replicate (replicate 1 only, to stay
within the account's weekly usage), order seeded (2030), parallel 3. No smoke run.

**Evaluation.** As §13 (`scripts/explore_dev.py`, a generalised copy of `explore_e1.py`): pairwise **E2 vs B** and
**E2 vs E1**, replicate 1, both orders; both absolute judges; the decision-completeness check with the §13
checklists (`eval/dev-e1/decision_reference`, unchanged).

**Reading rules, fixed now.** With five pairs per comparison these are directional only.
- E2 is the candidate for the held-out test if it beats E1 pairwise (overall preference > 0.5) without losing
  decision completeness. Otherwise E1 is.
- E2 vs B is reported as the remaining gap; the held-out target stays non-inferiority to B (≥ 0.45).

**Deviation during E2 generation (infrastructure, recorded as it happened).** The machine slept twice during the
run. `dev-e2-c3-E2-r1` attempt 1 hung after the first sleep (no transcript output for 40 minutes) and was stopped
by hand, which the harness records as an infrastructure failure and retries. A stall watchdog added before the
second sleep had a bug: it read the hung attempt's old transcript and stopped attempts 2–4 as they started, so the
run ran out of retries; an empty document then went through blinding, both absolute judges and four pairwise
calls. Those outputs and the run were moved to `runs/_aborted/dev-e2-c3-watchdog-bug/` (one of the two absolute
judgments was overwritten in the move; both scored an empty document), the blind id was withdrawn, and c3 was run
again from scratch with the same skill snapshot and prompt. No model output was rerun or selected: none of the
four aborted attempts produced a deliverable. The watchdog now reads only each run's newest attempt.

## 15. Development arm H1: compile mode on B's finished decks (hybrid direction)

**Why.** Across the main benchmark, C2, the slide review, E1 and E2, the six-line prompt (B) produced the stronger
analysis and the skill the stronger deliverable. Hybrid H lets the B prompt do the analysis and makes the skill
compile it into a deck without changing its meaning (`references/compile.md`, commit `1fd16ab`). H1 tests only the
compile step: can the skill carry a finished analysis onto slides with nothing decision-relevant lost? It does not
test reasoning. The design was agreed with an independent review (Codex) before any run.

**Design.** Input: B's deck for the same case, extracted to text (`extract/deck.txt`), plus the briefing pack. Source
decks: `main-c2-B-r3` and `main-c5-B-r2`, the two B decks of the author's slide review. Two variants: **H1s**
(`restyle`: keep B's slide order and structure, change design and wording style) and **H1r** (`restructure`: keep
the content, re-lay the argument). Phase `dev-h1`: 2 cases × 2 variants = 4 runs, order seeded (2031). Same model,
effort, tools, sandbox and auto-reply as before; skill snapshot includes the 1.2.1 renderer fix and compile mode.

**Primary outcome: content fidelity**, measured independently of the skill's own `compile` block.
- Fable 5.2 lists the decision units of each source deck (answer, recommendations with conditions, claims with
  their numbers, assumptions, ranges, alternatives, thresholds and gates, risks, decisions asked, next steps), marks
  each `critical` and `valid`. B's known errors from the main evaluation are given, so an invalid unit fixed by H1
  counts as a correction, not a loss. Written before any H1 deck is checked.
- Fable 5.2 then marks each unit in each H1 deck `preserved`, `altered`, `missing`, `corrected` or `still_wrong`, and
  lists new errors as critical, material or minor.
- Deterministic check: numbers in critical, valid units must appear in the H1 deck text.
- Correction log: the skill's self-reported `compile.corrections` and the checker's `corrected` units, reported apart
  from preservation.

**Secondary outcomes.** Pairwise H1 vs the source B deck (Fable 5.2, both orders, **prompt without word counts**,
`prompts/eval/judge_pairwise_nowords.md`); slides, words, cost, API time; `check.py` result; number classes in the
workbook (sourced, derived, estimate, untraceable); later, the author's slide review (not blind) and, if available,
blind reviewers.

**Reading rules, fixed now.** H1 passes on a deck if every critical, valid unit is preserved (target 100%; a single
critical unit altered or missing is reported by name), no critical new error appears, and `check.py` passes. The
variant comparison is descriptive (two cases). Pairwise preference is not a fidelity measure and decides nothing on
its own; it shows whether the compiled deck reads worse than its source.

**H1 results (2026-11-18; details in `results/dev-h1/tables.md`).** All 4 runs complete, audits clean, `check.py`
0 fails, source workbooks with 387–666 numbers each (103–592 derived; 3–7 critical numbers that could not be
traced, each acknowledged in the spec).
- Fidelity (critical, valid units preserved): c5 restyle 97/97, c5 restructure 96/97 (one claim missing: selling
  store-based delivery to grocers gives a share of market growth), c2 restyle 69/72, c2 restructure 67/72. Most c2
  "altered" units are rounding-level ($35.4M → $35.3M, 16.9 → 17.0, 38.0 → 37.9). Substantive: c2 restyle changed
